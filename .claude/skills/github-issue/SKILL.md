# GitHub 이슈 등록

저장소는 **public**이다. 이슈 본문은 누구나 볼 수 있고 검색에도 잡히므로, 올리기 전에 반드시 초안을 보여주고 승인을 받는다.

## 1. 내용 정리
대화에서 이슈로 남길 내용을 뽑는다. 부족하면 코드에서 직접 확인한다(추측으로 쓰지 않는다).
- 무엇이 문제인지 / 무엇을 할지
- 위치: `lib/...:줄번호` (저장소 상대 경로만)
- 버그면 재현 조건과 실제 동작 vs 기대 동작

## 2. 중복 확인
```bash
gh issue list --state all --search "<핵심 키워드>" --limit 10
```
- 비슷한 열린 이슈가 있으면 새로 만들지 말고 그 이슈에 체크리스트 항목이나 댓글을 추가할지 묻는다.
- 같은 내용이 닫혀 있으면 재발인지 사용자에게 확인한다.

## 3. 초안 작성
모든 이슈는 `.github/ISSUE_TEMPLATE/task.md`를 읽어 그 구조대로 쓴다(맨 위 `---` front matter는 본문에서 뺀다). 양식이 바뀌면 그 파일만 고치므로, 섹션 이름을 여기서 따로 외워 쓰지 않는다.

제목은 `[타입] 짧은 한국어 명사구` 형식이다(예: `[test] 진단 레포지토리 테스트`). 타입은 커밋 컨벤션(`.claude/commands/commit.md`)과 같은 키워드를 쓰고 쓴다.

| 타입 | 용도 | 라벨 | 배경에 쓸 것 |
|---|---|---|---|
| feat | 새 기능 | `enhancement` | 왜 필요한지 한 줄 |
| fix | 버그 수정 | `bug` | 증상과 원인 위치(파일:줄) 한두 줄 |
| refactor | 동작 변화 없는 구조 변경 | `enhancement` | 무엇을 왜 바꾸는지 한 줄 |
| test | 테스트 코드 | `enhancement` | 어떤 클래스를 왜 테스트하는지 한 줄 |
| design | UI·테마 스펙 반영 | `enhancement` | 무엇을 맞추는지 한 줄 |
| docs | 문서 | `documentation` | 무엇을 정리하는지 한 줄 |
| build | 패키지·빌드 설정 | `enhancement` | 무엇을 바꾸는지 한 줄 |
| chore | 기타 | 없음 | 무엇을 하는지 한 줄 |

- 사용자가 타입을 말하지 않으면 내용을 보고 고른 뒤 초안에서 확인받는다.
- 사람이 쓴 것처럼 짧게 쓴다. 배경은 1~2줄, 세부 작업은 "~ 구현", "~ 테스트" 같은 명사구 한 줄씩. 설명 문장 나열·대시(—)·가운뎃점 나열·백틱 남발은 넣지 않는다.
- 이미 끝낸 작업은 `- [x]`로 체크해서 넣는다.
- 참고 사항은 링크·에러 로그·관련 이슈가 있을 때만 쓰고, 없으면 섹션째 뺀다.
- 라벨은 `gh label list`에 있는 것만 쓴다. 새 라벨은 만들지 않는다.
- 2단계(대시보드·랭킹 등) 작업이면 타입 뒤에 `[2단계]`를 붙인다(예: `[feat][2단계] 대시보드 구현`).
- 본문은 scratchpad에 파일로 써서 `--body-file`로 넘긴다(따옴표·백틱 깨짐 방지).

## 4. 공개 전 점검
초안에 다음이 들어가면 빼거나 일반화한다.
- 키·토큰·App Check 디버그 토큰·keystore 정보, `.env`·`key.properties` 내용
- 사용자 이메일·uid·실제 대화 원문 등 개인 데이터
- 저장소 밖 로컬 경로(Obsidian 볼트, `~/Documents/...`)

## 5. 승인 후 등록 (쓰기 작업)
초안(제목·라벨·본문)을 그대로 보여주고 "올릴까요?"로 확인한 뒤 실행한다.
```bash
gh issue create --title "<제목>" --label "<라벨>" --assignee @me --body-file <scratchpad>/issue_body.md
```
- 출력된 이슈 URL과 번호를 보고한다.
- 커밋으로 해결할 때는 메시지에 `closes #번호`를 넣으면 push 시 자동으로 닫힌다고 안내한다(push는 사용자가 한다).

## 기존 이슈 수정
요청이 있을 때만, 승인 후 실행한다.
```bash
gh issue view <번호>
gh issue comment <번호> --body-file <파일>
gh issue edit <번호> --body-file <파일>      # 체크리스트 항목 추가·체크
gh issue close <번호> --comment "<사유>"
```
- 본문을 고칠 때는 `gh issue view`로 현재 본문을 먼저 읽고, 기존 항목을 지우지 않고 덧붙인다.

## 권한 경계
- 에이전트: 코드 확인, 중복 검색, 초안 작성, 승인 후 `gh issue create/edit/comment/close`
- 사용자: 초안 승인, `git push`
- 금지: 승인 없는 등록, 이슈 삭제(`gh issue delete`), 새 라벨·마일스톤 생성, 시크릿·개인 데이터 게시
